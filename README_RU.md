# Кредитный скоринг — Home Credit Default Risk

[🇬🇧 Read in English](README.md)

Учебный проект по бинарной классификации в рамках освоения логистической регрессии. Цель — построить модель кредитного скоринга, предсказывающую вероятность дефолта заёмщика по данным заявки, и научиться интерпретировать её результаты в терминах, понятных бизнесу.

Структура проекта повторяет подход из моего предыдущего проекта [hot-jupiter-detector](https://github.com/DigitalOcean78/hot-jupiter-detector): одна тетрадка, лаконичное оформление, акцент на интерпретации модели.

## Постановка задачи

**Тип задачи:** бинарная классификация.

**Целевая переменная:** `TARGET`
- `0` — клиент вернул кредит в срок (282 686, 91.93%);
- `1` — у клиента возникли трудности с платежами / дефолт (24 825, 8.07%).

**Что предсказываем:** вероятность дефолта `P(TARGET = 1 | X)` по признакам заявки.

**Метрики качества:**
- **ROC-AUC** и **Gini** (= 2·AUC − 1) — основная метрика в скоринге;
- **KS-statistic** — стандарт индустрии;
- **PR-AUC** — информативна при дисбалансе классов;
- **Brier score** — качество калибровки вероятностей.

**Особенности задачи:**
- сильный дисбаланс классов (дефолтов ~8%, соотношение ~11.4 : 1);
- стоимость ошибок несимметрична: пропущенный дефолт (FN) дороже ложной тревоги (FP);
- в реальном скоринге требуется высокая интерпретируемость модели.

## Описание данных

**Источник:** соревнование [Home Credit Default Risk](https://www.kaggle.com/c/home-credit-default-risk) на Kaggle.

**Используемый файл:** `application_train.csv` — заявки на кредит (одна строка = один клиент). Остальные файлы соревнования (bureau, previous_application и др.) в этом проекте не используются, чтобы сфокусироваться на моделировании и интерпретации, а не на join'ах.

**Размер:** 307 511 строк × 122 признака.

**Типы признаков:** 65 `float64`, 41 `int64`, 16 `object` (категориальные — под One-Hot).

**Известные аномалии и особенности данных:**
- `DAYS_EMPLOYED = 365243` — маркер «не работает» (пенсионер/безработный), требует замены на NaN и создания отдельного флага;
- `CODE_GENDER = 'XNA'` — единичные записи (4 шт.);
- структурные пропуски: блок housing (~47 колонок) полностью отсутствует у 47.4% клиентов и полностью заполнен у 25.6%;
- высокая кардинальность: `ORGANIZATION_TYPE` (~58 значений) и `OCCUPATION_TYPE` (~31) при One-Hot дадут много колонок.

## Методология

1. **EDA:**
   - Проанализированы пропуски (выявлена структурность в блоке housing).
   - Визуализированы распределения ключевых числовых признаков vs TARGET (`EXT_SOURCE_2/3` и `DAYS_BIRTH` показали отличное разделение).
   - Проанализирована доля дефолтов по категориальным признакам (`NAME_EDUCATION_TYPE` показал огромный разброс от 2% до 11%).

2. **Предобработка:**
   - Удалено 48 «мусорных» колонок (housing-блок с >30% пропусков + `OWN_CAR_AGE`).
   - Обработана аномалия `DAYS_EMPLOYED` (заменена на NaN + создан флаг `IS_UNEMPLOYED`).
   - Импутация пропусков (медиана для чисел, `'Unknown'` для категорий). Заполнение `OCCUPATION_TYPE` значением `'Unknown'` оказалось крайне эффективным.
   - Применён One-Hot Encoding к 12 категориальным колонкам (итого 175 признаков).
   - Данные разделены на Train/Test (80/20) со стратификацией для сохранения доли дефолтов 8.07%.
   - Признаки масштабированы через `StandardScaler` (обучен только на train во избежание утечки данных).

3. **Моделирование:**
   - Обучена `LogisticRegression` с `class_weight='balanced'` для компенсации дисбаланса классов.

4. **Интерпретация:**
   - Извлечены коэффициенты и переведены в Odds Ratio.
   - Выявлены главные факторы риска (`AMT_CREDIT`) и защитные факторы (`EXT_SOURCE_1/2/3`, `AMT_GOODS_PRICE`).

5. **Калибровка:**
   - Применена изотоническая регрессия (`CalibratedClassifierCV` с `FrozenEstimator`) для исправления переуверенных вероятностей, вызванных `class_weight='balanced'`.

## Результаты (на тестовой выборке)

| Метрика | Значение | Комментарий |
|---------|----------|-------------|
| ROC-AUC | 0.7485 | Отличный baseline для LogReg |
| Gini | 0.4971 | >0.4 считается сильным результатом в скоринге |
| KS | 0.3689 | >0.3 — индустриальный стандарт «хорошей» модели |
| PR-AUC | 0.2288 | В ~2.8x лучше случайного baseline (0.0807) |
| Brier (после калибровки) | 0.0685 | Вероятности откалиброваны и пригодны для бизнес-расчётов |

## Ключевые инсайты

1. **Сильнейшие признаки:** `EXT_SOURCE_1/2/3` (внешние скоринговые баллы), `AMT_CREDIT` (сумма кредита) и `AMT_GOODS_PRICE` (стоимость товара). Модель самостоятельно выявила те же сильные признаки, что были замечены на этапе EDA.
2. **Unknown как сигнал:** Заполнение `OCCUPATION_TYPE` категорией `'Unknown'` было верным решением. Признак `OCCUPATION_TYPE_Unknown` вошёл в топ-20 коэффициентов, доказав, что отсутствие данных коррелирует с риском.
3. **Калибровка критична:** Исходные вероятности сбалансированной модели имели Brier = 0.2026. После изотонической калибровки он упал до 0.0685, что делает вероятности пригодными для расчёта ожидаемых потерь (PD × LGD × EAD).

## Ограничения и возможные улучшения

- **Нет feature engineering:** Baseline использует только `application_train.csv`. Присоединение `bureau.csv` и `previous_application.csv` обычно добавляет +0.02–0.04 к AUC.
- **Нет WOE-биннинга:** Weight of Evidence — стандарт скоринга, улучшает интерпретируемость и иногда качество.
- **Тюнинг порога:** Используется дефолтный порог 0.5. В реальном бизнесе порог выбирается на основе матрицы стоимости ошибок (FN vs FP).
- **Нет out-of-time валидации:** В данных нет дат для проведения истинной временной валидации.

## Как запустить

1. Склонируйте репозиторий.
2. Скачайте `application_train.csv` со страницы соревнования Kaggle и положите в папку `data/`.
3. Установите зависимости: `pip install -r requirements.txt`
4. Откройте и запустите тетрадку: `jupyter notebook notebooks/credit_scoring.ipynb`
